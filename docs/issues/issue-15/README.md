## 摘要

```js
export const TOKEN_SPLIT_PATTERN = /[^a-z0-9一-鿿]+/
```

CJK 字元全部被視為 token 內字元，而中文沒有空白分隔，所以**一整句中文問句 tokenize 之後是一個 token**。那個 token 接著被要求「整句逐字出現」才算匹配——自然語言問句幾乎必然落空。

關鍵在於 `tokenizeQuery` 同時餵兩條路：`tokenCoverage`（評分／`confidence`）**與**檢索用的查詢構成。issue-9 已經記過這個 tokenizer 行為，但當時把後果侷限在「confidence 回報失真」。實測顯示它也**吃掉召回結果**——比 issue-9 描述的嚴重一級：不是分數難看，是真的召不到。

### 一個不算證據的案例，記下來免得誤導

`停 伺服器 行程` → 0 筆。這**不是** tokenizer 問題：使用者的記憶寫的是 `server` 不是 `伺服器`，也沒有 `行程` 二字。那是詞彙差異，正確行為就是 0 筆。分析時差點把它算進去。

## 根因

**不是 FTS 索引的能力問題。** `recall_fts` 用的是 `tokenize='trigram'`（`schema.ts:57`），trigram 本來就能做 CJK 子字串匹配——上表前兩列證明了連續中文子字串確實命中。

問題出在**我們餵給它什麼**：`tokenizeQuery` 把整句交出去，於是 trigram 匹配退化成「整串必須連續出現」，LIKE fallback（`%整句%`）同樣是逐字比對。索引有能力，查詢沒有給它機會。

## 影響面

- **本 repo 使用者的日常路徑，而且沒有東西在遮它**：`CLAUDE.md` 要 agent 執行 `memoria recall "<查詢>"`，而 **`recall` 的預設模式就是 keyword**（`memoria.ts:470`，`filter.mode ?? 'keyword'`）——`vector` 只在明確下 `--mode vector` 時才跑。所以「反正有語意召回頂著」是錯的：預設路徑的落空是完全暴露的。（此點由 downstream-cli-container 更正，本 session 已於程式碼查證。原先誤以為已啟用語意召回的部署會被 vector 遮掉。）
- **每個下游都得各補一次**：下游已在呼叫端自行切詞解決，但那是一份活在 Memoria 之外的實作。這與 issue-13 決定讓 `/v1/brief` 回傳 `data.markdown`、而非讓每個呼叫端自己重寫 `renderBrief` 是**同一個論證**。

## 下游回饋（2026-08-13，兩個獨立部署）

### 只改查詢端就夠——理由比「不用重建索引」更強

downstream-cli-container 今天在**自己的 repo** 修掉同一類 CJK tokenize 缺陷，而他們**兩側都得改**。差別在索引的 tokenizer：

| | 索引 tokenizer | 只改查詢端夠嗎 | 為什麼 |
|---|---|---|---|
| Memoria `recall_fts` | `trigram` | **夠** | 索引的是每個 3 字元視窗，查詢端切出的短 token 只要 ≥3 字元就以子字串命中，文件側不必動 |
| 那個下游的 FTS | `unicode61` | **不夠** | 比對的是 **token 等值**，文件側那顆大 token 與任何短查詢 token 都不相等，必須加欄位存展開形式並重建索引 |

這是一個獨立來源的架構對照，結論與本 issue 的傾向一致，但把理由講得更準：**不是「不用重建比較省事」，而是這個索引本來就有能力，是查詢把它退化掉的。** 動工時不要把這個結論當成通則帶去別處——它成立的前提是 trigram。

（參考量級：該下游的遷移是回填 + FTS rebuild，5,000 列 232 ms。Memoria 不需要重建，此數字僅供日後真要重建時估算。）

### 沒有下游依賴目前的 tokenize 或 confidence 數值

downstream-cli-container 確認：agent 讀的是 CLI 的文字輸出，`feedback --score` 由 agent 自行判斷而非從 `confidence` 推導，也沒有任何程式解析 tokenize 行為。純查詢端改動碰不到他們自帶的 helper。**這降低了改動的外部風險**，但不改變與 issue-9 的內部耦合（`confidence` 數值分佈仍會變，那仍需明示決定）。

### ⚠ 想量測影響面的話，`token_count` 是錯的代理指標

該下游試著用既有 telemetry 的 `token_count` 當「整句中文」的代理，**失敗了**：

```
token_count=1   12 次，落空 4 次 → 33%
token_count>1   14 次，落空 5 次 → 36%
```

沒有差異甚至反向。原因是這個代理把兩種相反的情況混在同一格：`token_count=1` 同時包含**短中文詞**（trigram 撈得到，會命中）與**長中文句**（撈不到），訊號互相抵銷。本 issue 針對的只有後者。

要量到真正的東西，需要的是查詢的**最長 token 字元數**——它能區分 `記憶` 與 `停止伺服器行程要注意什麼`，而且不洩漏查詢內容（`recall_telemetry` 目前只存 `query_hash`，事後補算不出來）。

**若要在修正前後做量化對照，得先加這一欄。** 那是本 issue 的前置作業，也是它值得單獨評估的一小塊——加了之後才有辦法回答「這個缺陷實際吃掉多少召回」。

（**歸屬更正，2026-08-17**：那份 `recall_telemetry` 分佈原記為「該下游自己的資料」，實際來源是 `~/.memoria` ——**本 repo 維護者自己的 store**，只是先前由下游 session 去量的。該下游的生產記憶庫是空的（0 memories / 0 telemetry），而且它有自己的召回引擎（FTS5 unicode61 + 自建 bigram），與 Memoria 是不同的程式碼路徑；Memoria 在那邊只是容器內給 agent 用的 CLI。所以那組數字從來不是「下游使用 Memoria 的實況」。

重量後的數字也與原記錄不同（49 筆：keyword 29 次落空 9 次＝31.0%；`token_count=1` 29.6% vs `>1` 22.7%），回報者明說樣本在期間變過、不去反推對齊。無論如何**兩組都被診斷查詢汙染，只能當量級參考**。）

### 消融實驗定案兩項：用 2-gram、不要停用詞表

downstream-http-sidecar 做了消融（拋棄式 1.27.0 + 5 輪中文語料 + 5 個中文查詢）：

| 策略 | 命中查詢 | 總命中 | 平均 conf | route |
|---|---|---|---|---|
| 原句（不切） | 2/5 | 2 | 0.300 | fallback×3, tree×2 |
| **2-gram 不斷句** | **5/5** | **7** | 0.605 | tree×5 |
| 2-gram + 停用詞斷句 | 5/5 | 7 | 0.650 | tree×5 |
| 3-gram 不斷句 | 3/5 | 3 | 0.463 | fallback×2, tree×3 |
| 3-gram + 停用詞斷句 | 3/5 | 3 | 0.440 | fallback×2, tree×3 |

**（1）不要內建中文停用詞表。** 斷句與不斷句的召回**完全相同**（都是 5/5、7 筆）；停用詞只讓 `confidence` 高 0.045，而那是因為它把噪音 token 從 `relevance = 命中數 / 查詢 token 數` 的分母移掉——**報數變好看，不是找得比較準**。為 0.045 的分母效果引進一份需要人維護的詞表，與本 repo 一整條「消滅手動維護清單」的方向相反。

**（2）用 2-gram，不要 3-gram。** 3-gram 明顯更差（3/5 vs 5/5），且 route 分布顯示它根本沒走到 FTS。這推翻了「3-gram 能對齊 trigram 索引因而吃到 bm25」的直覺——提出者自己也是先猜錯再被實驗推翻的。

### ⚠ 實作細節：命中會落在 tree route，不是 FTS

上表 2-gram 的命中**全部來自 tree route**（`haystack.includes`），不是 bm25。原因是 `FTS_MIN_TERM_LEN = 3`（`recall.ts:404`），而 `buildFtsMatch` 用 `tokenizeQuery(query, FTS_MIN_TERM_LEN)`（`:433`）——**2 字 token 會被濾光**。

所以「不動索引」是對的，但別預期改完就會走 bm25。動工時要明確決定：接受效果落在 tree/LIKE 路徑，或一併調整 `FTS_MIN_TERM_LEN` 對 CJK 的處理（後者是額外範圍，且 trigram 索引最短就是 3 字元，2 字 token 本來就吃不到 FTS）。

### 精確度代價：在有標籤的真實語料上量過了

downstream-http-sidecar 在 891 筆**自帶 ground truth** 的真實記憶上量測（每筆的任務前綴就是標籤，5 個語意鄰近但可區分的類別）。查詢字串由**產品程式碼實際產生**並攔截，不是另外複寫一份切詞邏輯：

| 期望標籤 | 原句（命中, 精確） | 2-gram（命中, 精確） |
|---|---|---|
| Crypto Monitor | 0 筆, — | 5 筆, p=0.80 |
| GitHub Trending | 5 筆, p=1.00 | 5 筆, p=1.00 |
| 早安市場分析 | 0 筆, — | 5 筆, p=1.00 |
| 盤前台股催化劑 | 0 筆, — | 5 筆, p=1.00 |
| 晚間市場分析 | 0 筆, — | 5 筆, p=1.00 |

```
原句  ：命中查詢 1/5，總回傳  5 筆，精確度 1.000
2-gram：命中查詢 5/5，總回傳 25 筆，精確度 0.960
```

**召回 5 倍，精確度掉 4 個百分點**，25 筆裡只有 1 筆越界。

**三個但書必須跟著這組數字一起讀**（回報者自己標註的，照抄以免被高估）：

1. **原句的 1.000 是假的高分**——它只在 1/5 查詢命中、只回 5 筆。幾乎不撈東西的策略精確度當然是 1。這組對照能說的是「2-gram 用 4% 精確度換 5 倍召回」，不是「原句比較準」。
2. **那唯一一筆越界有爭議**：查「今天比特幣跟以太坊行情怎麼樣」回了一筆「晚間市場分析」，而那份報告內容真的談加密貨幣。算不算誤命中取決於標籤定義，不是召回品質。真實越界率可能更低。
3. **這是偏難的語料**——5 個類別語意鄰近，市場分析類三個標籤共用大量詞彙。主題分散的語料應該更好不會更差。

**判讀要保守**：只有 5 個查詢，n 很小。正確的結論是「**沒有發現災難性的精確度崩壞**」，而不是「精確度是 0.96」。動工後仍應在本 repo 自己的語料上再驗一次。

### 過渡開關：要有，但是過渡工具不是永久選項

下游打算在本功能落地後拿掉自己那層，但需要一個開關做 A/B（用他們的切法 vs 用 Memoria 的，在自己語料上比一次）。

他們同時指出一個比「重複切分變差」更難察覺的後果：**他們送出的已是空白分隔的 2 字詞，Memoria 再切也切不出更小的，所以會變成他們的切法蓋過我們的、我們的實作實質 no-op**——升級後行為由較舊的那層決定，而且不會有任何跡象。

因此開關的定位要寫死在文件裡：**過渡期工具，A/B 完成即移除**。永久保留一個「關掉中文切詞」的旗標，只會變成下一個沒人記得為什麼存在的東西。

## 實作結果（2026-08-14）

### ⚠ 動工後才發現：對 `keyword` 路徑，單純的 2-gram 會比不改更糟

下游的成功經驗是 2-gram，但那是在 **hybrid／tree** 路徑上量的。本 repo 使用者的預設是 **`keyword`**，而那條路徑的構造完全不同：

```
buildFtsMatch(query) = tokenizeQuery(query, FTS_MIN_TERM_LEN=3) → OR-join → FTS5 MATCH
  ↓ 若 FTS 回 0 筆
queryRecallLike(db, query, …)   ← 用的是「原始查詢字串」的 %query%，不是 token
```

若照抄 2-gram：長度 2 全部低於 `minLength=3` 被濾光 → **MATCH 字串變空 → 跳過 FTS → 退回逐字 LIKE**，結果比原本（至少還把整句送進 FTS 試一次）更糟。

**修法因此是「n 由呼叫端的 `minLength` 決定」**，而不是固定 2：

| 呼叫端 | minLength | CJK 展開 | 為什麼是對的 |
|---|---|---|---|
| `buildFtsMatch` | 3 | 3-gram | `recall_fts` 是 **trigram** 索引，3 字視窗正是它儲存的單位，能以子字串命中 |
| `tokenCoverage` / tree | 2 | 2-gram | 用 `includes` 比對，視窗越短越能命中改寫過的說法 |

每個消費端本來就在宣告「我能用的最短詞長」，而那個數字對 CJK 恰好就是正確的視窗大小——所以這不是額外的參數，是既有參數的正確解讀。拉丁字與數字的連續段維持完整不切。

### 實測（使用者真實 `~/.memoria` 的複本，13 sessions / 37 decisions）

12 個自然語言中文問句，每題的答案都確實存在於語料中但**措辭不同**：

```
修正前  命中查詢 6/12  ｜ 總回傳 21 筆 ｜ 期望答案有出現 5/12
修正後  命中查詢 8/12  ｜ 總回傳 24 筆 ｜ 期望答案有出現 7/12
```

**精確度沒有崩**：總回傳只從 21 增為 24，而正確答案從 5 增為 7。抽查兩筆新命中：

- `停止伺服器行程要注意什麼` → 只回 1 筆，正是「停 Memoria server 一律用 PID 精準停」
- `版控文件可以寫真實名稱嗎` → 回 2 筆，皆為隱私兩層區隔相關

兩者的 `route_mode` 都是 `keyword`——**FTS 真的在做事**，不是退到 fallback。

### `confidence` 跟著新切分走（使用者拍板）

`tokenCoverage` 與檢索共用 `tokenizeQuery`，所以 confidence 的數值分佈必然改變。三個選項評估後由使用者選定**跟著走**：

| | 跟著走（採用） | 維持舊尺度 |
|---|---|---|
| 上面兩個正確命中 | 0.18 / 0.55 | **0.00 / 0.00** |

不跟著走的話，中文整句查詢的正確命中會回報 confidence 0——**那正是 [issue-9](../issue-9/README.md) 剛判定為錯誤的形態**（命中正確卻回報 0），只是從語意路徑換到字面路徑。

**已知代價**：分數被無意義的窗格稀釋（`器行`、`程要` 這類永遠不會命中），所以中文查詢的 confidence 結構性低於英文，**跨語言不可比**。`confidence_basis` 已載明尺度來源是 `lexical_coverage`，本來就沒有宣稱跨語言可比性；但判讀時要記得。

### ⚠ 給下游的重要更正：`hybrid` 兩條路都跑，所以預切詞的下游現在就在付代價

本 issue 發版後，通知下游時我判斷「用 `hybrid` 的下游因為 `minLength=2`，自己預切 2 字詞大致沒事」。**那是錯的**，由 downstream-http-sidecar 讀碼更正、本 session 查證確認（`memoria.ts:483-488`、`:539`）：

```ts
const treeRaw    = mode !== 'keyword' && mode !== 'vector' ? recallTree(...)    : []
const keywordRaw = mode === 'tree'                         ? []                 : recallKeyword(...)
```

`hybrid` 下**兩者都無條件執行**，然後 merge。`fallbackUsed` 是事後從「有沒有 keyword 專有結果存活」判斷的，**不控制 keyword 跑不跑**。

所以一個把中文預切成空白分隔 2 字詞的 hybrid 呼叫端是「一邊活一邊死」：

| hybrid 的一半 | minLength | 送 2 字詞的結果 |
|---|---|---|
| tree（`scoreNode` + `includes`） | 2 | 存活，正常命中 |
| keyword（`buildFtsMatch` → trigram） | **3** | 被長度過濾 → MATCH 空 → 退回帶著插入空白的 `%…%` LIKE |

**結論比原本更強**：不是「未來改用 keyword 才會變差」，而是**現在已經在損失 keyword 那半邊的貢獻**，只是被 tree 撐住所以看不出來。預切詞的下游應該拿掉自己那層，不是維持現狀。

順帶修掉一個同型的文件缺陷：`memoria.ts:539` 的註解原本寫 `prefer tree route, then merge keyword fallback if needed`——那個 `if needed` 描述的是程式沒有實作的意圖，而它正是我判斷錯誤的來源。註解已改成陳述實際行為，並寫明沒有「if needed」。

### 仍然召不回的 4 題，以及為什麼不是這個 issue 能解的

`容器裡那份記憶跟本機有關係嗎` / `這次發版號要怎麼選` / `截斷資料的時候要不要提示` / `骨架的促升要怎麼擋` 仍是 0 筆。

原因是**詞彙差異而非切分**：例如記憶寫「context 截斷永不靜默」，查詢問「截斷資料的時候要不要提示」——共用的只有「截斷」兩字，而 trigram 索引最短就是 3 字元，2 字詞在 FTS 上不可達。要解這類需要**語意召回**（`--mode vector`），那是既有能力而非本 issue 的範圍。

分析時要小心不要把這類算成 tokenizer 的失敗——本 issue 的文件與新增的純函式測試各記了一次這個陷阱，因為我在寫測試時自己又踩了一遍。

### ⚠ 但有一個殘留缺陷不是詞彙問題，而且成因已定位（2026-08-17）

下游觀察到、本 session 在維護者語料上重現：**中文單詞命中，中文片語即使兩半都在語料裡也回 0，而結構相同的英文可以。**

```
記憶            → 5 hits   route=keyword
召回            → 3 hits   route=keyword
記憶召回        → 0 hits   route=keyword     ← 兩半都在語料裡
記憶的召回機制  → 0 hits   route=keyword
memory recall   → 3 hits   route=keyword     ← 英文同構查詢可以
```

配上 token 分析，成因是**兩個機制疊起來**：

| 查詢 | `tokenizeQuery(q, 3)` | 實際走的路 |
|---|---|---|
| `記憶` | `[]`（2 字 run 低於門檻被濾） | MATCH 空 → 跳過 FTS → **LIKE `%記憶%`** → 命中 |
| `記憶召回` | `["記憶召","憶召回"]` | 兩個都**跨詞邊界**、語料中不存在 → FTS 0 → 落到 LIKE `%記憶召回%`**逐字** → 0 |
| `memory recall` | `["memory","recall"]` | FTS **OR** 語意，任一命中即可 → 命中 |

也就是說：**英文多詞查詢拿到 OR 語意，中文多字查詢拿到「連續子字串」語意。** 兩個原因缺一不可：

1. 對 4 字查詢，本 issue 產出的 3-gram **全部跨越詞邊界**（`記憶召`、`憶召回`），而真正承載語意的 `記憶`、`召回` 是 2 字、在 FTS 路徑上不可達。
2. **`queryRecallLike` 比對的是「整個原始查詢字串」而不是 token**（`recall.ts:523`，`const q = '%' + query.toLowerCase() + '%'`）。所以 FTS 落空後的救援網本身也是逐字的。

**這是本 issue 的殘留缺陷而非詞彙差異**，因為答案確實在語料裡、而且英文同構查詢找得到。修法方向是讓 LIKE fallback 對 token 做 OR 而不是比對整句——`記憶召回` 就會變成 `%記憶% OR %召回%`。

**但不要順手改**：LIKE 路徑沒有 bm25 排序（`ORDER BY timestamp DESC`），對 2-gram 做 OR 可能撈回一批「時間近但不相關」的列。這需要量測，所以另案處理。

（過程紀錄：第一次重現時暫存的語料複本已被 /tmp 清掉，`recall` 走了 `!existsSync(dbPath)` 的早期返回、回傳空結果且 `latency_ms: 0`——那組全 0 是在量一個不存在的資料庫。重建後才得到上表。與本 issue 反覆出現的教訓同型：一個看起來成立的量測可能量的是別的東西。）

### 測試

`scripts/pure-fn-driver.mts` 新增 6 條斷言釘住視窗規則，其中最重要的是「同一段 CJK 在 minLength 2 與 3 下產出不同 n-gram」——那條規則微妙到看起來像意外，沒有斷言的話很容易被後人「簡化」成固定 2-gram，而那正是會讓 `keyword` 路徑退步的改法。
