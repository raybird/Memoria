# Issue 30 - 技術方案與取捨

## 技術可行性

現有 Node HTTP server、TypeScript、SQLite 與 esbuild 足以交付本機記憶 viewer。Core 保持業務入口；HTTP 僅驗證與轉接，瀏覽器不讀取 SQLite、不把任意本機路徑交給後端開檔。預計不需要資料庫 migration，也不新增 runtime 依賴。

## 方案選型與取捨

### 同源內嵌 UI 與獨立前端服務

建議選同源內嵌 UI：

```diff
 使用者啟動本機記憶 UI
- 分別啟動前端與 API，設定位址及跨來源規則
+ memoria serve --ui 啟動同一個明確限制為本機的 HTTP 入口
 發布
- 打包 CLI，另分發前端靜態目錄與查找路徑
+ 前端先建置，再將 HTML／CSS／JS 內嵌於既有 CLI bundle
```

同源方式降低啟動與安裝差異，代價是前端變更也需重建 CLI。此規模可接受；開發預覽可用既有 CLI，不為首版新增常駐前端 dev server。

### 現有工具與新增前端框架

建議先使用現有 TypeScript／esbuild，以明確狀態模型與小型 DOM 元件組成。商品級品質依設計規則、語意化元件、狀態完整性與驗證證據判定，不依框架名稱判定。若實作實證顯示維護負擔需要框架，再提出具體依賴及取捨；目前不預先增加 React、路由器、UI kit、測試框架或 CSS 編譯工具。

### 即時權威查詢與靜態匯出頁面

靜態匯出成本較低，但容易過期，無法忠實反映被取代記憶、範圍切換與新的搜尋結果。建議採每頁查詢的本機 API；列表只回傳摘要，詳情才載入完整事件。保留 SQLite 為唯一真相，不另建 UI 專用記憶資料庫。

### 瀏覽單位

提案：預設列出 DecisionMade 事件；技能頁列出 SkillLearned 事件；session 分類列出 session。使用原始 ref_id 做固定網址及標記查詢，父 session 作為關聯。這比對所有 session 自動合併、去重、推導「邏輯筆數」更可解釋，且不改 recall 排名。Q3 已於 2026-10-25 獲核准，採用此分類。

## 架構影響

新資料方法以 public Core 對外，新增型別維持 `MemoriaResult<T>`。讀取列表與詳情使用參數化 SQL，已知 registry 名稱作為精確範圍依據；不透過 export 全量下載再於前端過濾，也不修改原 summary API 的既有 response shape。

UI 模式是一個明確受限的 router 設定：loopback 監聽、Host／Origin 驗證、固定資產路由與明列資料路由。業務寫入不掛載；明確搜尋可以走既有 recall，其 telemetry 副作用需被文件與資料驗收區分。原 `serve` 模式保持既有功能，不悄悄改成唯讀或縮小其監聽範圍。

初版以安全文字／結構化區塊閱讀記憶；不執行來源 HTML，不為保留 Markdown 外觀而先新增 sanitizer 依賴。若支援連結，限定安全協定與明確的外部連結行為。UI 資產內嵌，CSP 與資產 header 共同限制外部連線和 script 執行來源。

## 實作細節

- 列表採固定上限 50 的分頁，排序包含穩定 ID；以獨立 fixture 斷言同時間資料不漏不重複。若改用 cursor，保留使用者可恢復上一頁的行為。
- 詳情按原始 ref ID 取得完整結構化內容、父 session、marker 與既有 Git provenance；舊資料缺欄位時保留原文與明確缺項。
- 搜尋由使用者提交，透過取消與請求序號隔離過期 response；不在前端重算 confidence。
- 明確區分列表、搜尋結果、brief 的資料來源與範圍語意。brief 沿用現有共用資訊政策；repository 列表篩選則依 Q3 的確切範圍。
- 網址只保留可恢復的產品狀態；不要把完整記憶內容、資料根路徑或 runtime 設定塞入 query string。搜尋字串留在本機網址的行為需於正式文件說明。
- 載入、空資料、無結果、404、連線失敗及語意降級分開建模，重試保留條件且可取消。
- 視覺 tokens、互動狀態與文字規範在 UI 原始碼中單點維護；來源脈絡為主要識別設計，其餘版面保持閱讀導向。
