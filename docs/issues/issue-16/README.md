## 摘要

v1.28.0 之後，中文**單詞**召得回、中文**片語**即使兩半都在語料裡仍然回 0，而結構相同的英文查詢可以：

```
記憶            → 5 hits   route=keyword
召回            → 3 hits   route=keyword
記憶召回        → 0 hits   route=keyword     ← 兩半都在語料裡
記憶的召回機制  → 0 hits   route=keyword
memory recall   → 3 hits   route=keyword     ← 英文同構查詢可以
```

一句話：**英文多詞查詢拿到 OR 語意，中文多字查詢拿到「整串必須連續出現」語意。**

這**不是**詞彙差異（issue-15 已記錄的那類「記憶寫 server、查詢問伺服器」）。答案確實在語料裡，而且同結構的英文查詢找得到。

## 根因：兩個機制疊加，缺一不可

| 查詢 | `tokenizeQuery(q, 3)` | 實際走的路 |
|---|---|---|
| `記憶` | `[]`（2 字 run 低於門檻被濾光） | MATCH 空 → 跳過 FTS → **LIKE `%記憶%`** → 命中 |
| `記憶召回` | `["記憶召", "憶召回"]` | 兩個都**跨詞邊界**、語料中不存在 → FTS 回 0 → 落到 LIKE `%記憶召回%` **逐字** → 0 |
| `memory recall` | `["memory", "recall"]` | FTS **OR** 語意，任一命中即可 → 命中 |

1. **對短的 CJK 查詢，3-gram 幾乎全是跨詞邊界的垃圾。** `記憶召回` 產出的 `記憶召` / `憶召回` 兩個都橫跨語意邊界，語料中永遠不會出現；而真正承載語意的 `記憶`、`召回` 是 2 字，在 trigram 索引上**結構性不可達**（索引單位就是 3 字元）。

2. **FTS 落空後的救援網本身也是逐字的。** `queryRecallLike`（`recall.ts:523`）用的是
   ```ts
   const q = `%${query.toLowerCase()}%`
   ```
   ——**整個原始查詢字串**，不是 token。所以第 1 點漏掉的東西，第 2 點也接不住。

單詞之所以可行，是因為它讓 MATCH 變空、直接掉進 LIKE，而單一個詞的 `%記憶%` 恰好就是對的查詢。**片語反而更糟**，因為它產出了非空但無用的 MATCH，然後掉進一個逐字的 LIKE。

## 修法方向

**讓 LIKE fallback 對 token 做 OR，而不是比對整句。** `記憶召回` 就會變成 `%記憶% OR %憶召% OR %召回%`——`憶召` 撈不到東西是無害的，`記憶` 與 `召回` 會命中。

不採用的替選方案，理由先記著免得重議：

| 方案 | 不採用的理由 |
|---|---|
| 降低 `FTS_MIN_TERM_LEN` | trigram 索引的單位就是 3 字元，2 字詞在它上面不可達，改門檻不會讓它變得可查 |
| FTS 額外送 2 字詞 | 同上，而且會被自己的長度過濾擋掉 |
| 引入中文斷詞（辭典／jieba 類） | 需要新依賴與一份要人維護的辭典。issue-15 已用消融實驗否決過同性質的停用詞表（對召回零貢獻），且與本 repo「消滅手動維護清單」的方向相反 |

## ⚠ 動工前必須量測的：精確度

LIKE 路徑**沒有 bm25 排序**——`queryRecallLike` 是 `ORDER BY e.timestamp DESC LIMIT ?`。對 2-gram 做 OR 之後，它會變成「含有任一 2-gram 的最新 N 筆」，而長中文句能產出十幾個 2-gram，其中多數是跨邊界的噪音。**這可能撈回一批「時間近但不相關」的列。**

這是本 issue 唯一真正的風險，而且 issue-15 的經驗說明它必須量而不是推論——當時「固定 2-gram」看起來明顯正確，實測才發現它會讓 keyword 路徑退步。

值得一併評估的緩解：**讓 LIKE 結果依「命中了幾個相異 token」排序**，而非純時間序。那等於在沒有 bm25 的路徑上補一個廉價的覆蓋率排序，讓 OR 的放寬不至於直接變成雜訊。這會改變 LIKE 路徑的既有排序行為，需要單獨確認。
