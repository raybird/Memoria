## 摘要

v1.28.0 之後，中文**單詞**召得回、中文**片語**即使兩半都在語料裡仍然回 0，而結構相同的英文查詢可以：

```
記憶            → 5 hits   route=keyword
召回            → 3 hits   route=keyword
記憶召回        → 0 hits   route=keyword     ← 兩半都在語料裡
記憶的召回機制  → 0 hits   route=keyword
memory recall   → 3 hits   route=keyword     ← 英文同構查詢可以
```

一句話：**英文多詞查詢拿到 OR 語意，中文多字查詢拿到「整串必須連續出現」語意。**

這**不是**詞彙差異（issue-15 已記錄的那類「記憶寫 server、查詢問伺服器」）。答案確實在語料裡，而且同結構的英文查詢找得到。

## 根因：兩個機制疊加，缺一不可

| 查詢 | `tokenizeQuery(q, 3)` | 實際走的路 |
|---|---|---|
| `記憶` | `[]`（2 字 run 低於門檻被濾光） | MATCH 空 → 跳過 FTS → **LIKE `%記憶%`** → 命中 |
| `記憶召回` | `["記憶召", "憶召回"]` | 兩個都**跨詞邊界**、語料中不存在 → FTS 回 0 → 落到 LIKE `%記憶召回%` **逐字** → 0 |
| `memory recall` | `["memory", "recall"]` | FTS **OR** 語意，任一命中即可 → 命中 |

1. **對短的 CJK 查詢，3-gram 幾乎全是跨詞邊界的垃圾。** `記憶召回` 產出的 `記憶召` / `憶召回` 兩個都橫跨語意邊界，語料中永遠不會出現；而真正承載語意的 `記憶`、`召回` 是 2 字，在 trigram 索引上**結構性不可達**（索引單位就是 3 字元）。

2. **FTS 落空後的救援網本身也是逐字的。** `queryRecallLike`（`recall.ts:523`）用的是
   ```ts
   const q = `%${query.toLowerCase()}%`
   ```
   ——**整個原始查詢字串**，不是 token。所以第 1 點漏掉的東西，第 2 點也接不住。

單詞之所以可行，是因為它讓 MATCH 變空、直接掉進 LIKE，而單一個詞的 `%記憶%` 恰好就是對的查詢。**片語反而更糟**，因為它產出了非空但無用的 MATCH，然後掉進一個逐字的 LIKE。

## 修法方向

**讓 LIKE fallback 對 token 做 OR，而不是比對整句。** `記憶召回` 就會變成 `%記憶% OR %憶召% OR %召回%`——`憶召` 撈不到東西是無害的，`記憶` 與 `召回` 會命中。

不採用的替選方案，理由先記著免得重議：

| 方案 | 不採用的理由 |
|---|---|
| 降低 `FTS_MIN_TERM_LEN` | trigram 索引的單位就是 3 字元，2 字詞在它上面不可達，改門檻不會讓它變得可查 |
| FTS 額外送 2 字詞 | 同上，而且會被自己的長度過濾擋掉 |
| 引入中文斷詞（辭典／jieba 類） | 需要新依賴與一份要人維護的辭典。issue-15 已用消融實驗否決過同性質的停用詞表（對召回零貢獻），且與本 repo「消滅手動維護清單」的方向相反 |

## ⚠ 動工前必須量測的：精確度

> **本節原本寫「LIKE 路徑沒有 bm25 排序」——那是錯的，動工時讀碼才發現。** `queryRecallLike` 的 SQL 只用 `ORDER BY timestamp DESC` **挑候選**，取回之後 JS 層會用 `scoreNode`（token 覆蓋 × 時間衰減）重新排序（`recall.ts:582-590`）。所以「補一個覆蓋率排序」這個緩解方向不必做，它已經存在。
>
> 真正的風險是另一件事：**SQL 的 `LIMIT topK` 會在評分之前就砍掉候選**。放寬 WHERE 而不放寬取回量，只會讓更多「時間近」的列擠掉相關的舊列，而評分器根本看不到它們。

長中文句能產出十幾個 2-gram，多數是跨邊界的噪音，所以 OR 放寬確實會擴大候選集。issue-15 的經驗說明這必須量而不是推論——當時「固定 2-gram」看起來明顯正確，實測才發現它會讓 keyword 路徑退步。

## 實作與量測結果（2026-08-17）

**修法**：`queryRecallLike` 的 WHERE 改成對 token 做 OR，**並把整句查詢保留為 OR 的其中一項**（精確片語是這條路徑上最強的訊號，留著也保住既有行為）。同時 over-fetch：候選取回量改為 `topK × LIKE_OVERFETCH_FACTOR`（4），理由如上——不放寬取回量的話放寬 WHERE 是自我抵銷的。`recall-vector.ts` 的融合前 over-fetch 是同一個前例。

12 題評測集（5 題片語目標 + 4 題 issue-15 已修好的回歸 + 3 題長句用來觸發 OR 風險）：

```
修正前  命中查詢  6/12 ｜ 總回傳 11 筆 ｜ 期望答案有出現  5/12
修正後  命中查詢 12/12 ｜ 總回傳 38 筆 ｜ 期望答案有出現 10/12
```

### 精確度代價是真的，而且形態很集中

| 查詢 | 結果 |
|---|---|
| `記憶召回` | 5 筆**全部相關**，排序合理（相關者 0.67 在前，較弱者 0.33 在後） |
| `請告訴我所有跟測試還有驗證有關的事情` | 1 筆雜訊——但**修正前也是同一筆**，無退步 |
| `發版流程` | 5 筆中**只有 1 筆勉強相關**。`流程` 是常見詞，OR 把所有含它的記憶都撈進來 |

雜訊集中在**由常見詞組成的短中文查詢**。`發版流程` 從「0 筆」變成「5 筆裡 4 筆雜訊」——就注入 context 的成本而言，那一題是**退步**的。

**沒有便宜的分離方法**：雜訊的 relevance 是 0.33（3 個 token 命中 1 個），但 `停止伺服器行程要注意什麼` 的**正確**命中是 0.18（11 個 token 命中 2 個）。一個固定的 relevance 門檻會先砍掉後者。要真正分離需要詞頻資訊（idf 之類），而這條路徑上沒有。

**取捨判斷**：接受這個代價。主效果是 5 題原本回 0 的查詢拿回正確答案；雜訊有 `relevance` 與 `confidence` 標示（0.33 vs 0.67），且 `topK` 把損害上限鎖在 5 筆。修正前那些查詢是**什麼都沒有**，所以不存在「乾淨狀態被弄髒」——`發版流程` 是從無用變成「多數雜訊 + 一筆相關」。

若日後雜訊在實際使用中造成困擾，下一步是詞頻加權而非固定門檻，那需要另一個 issue。

### 不要等下游的落空率資料（2026-08-17）

兩個下游都確認**短期內產不出有代表性的樣本**，所以本 issue 與 [issue-15](../issue-15/README.md) 的量測就是目前能拿到的全部：

- downstream-cli-container：容器內自己的 Memoria store 幾乎是空的（sessions=1 / events=1），中文召回的改善無從顯現；他們主機上那份 `~/.memoria` 是**本 repo 維護者的** store 且 49 筆全部早於 v1.28.0。
- downstream-http-sidecar：可召回語料 15 筆（scope 分區後），且他們的 8 題 A/B 已經跑完，n 比本 repo 的 12 題還小。

也就是說**「等真實使用累積再判斷」在可預見的時間內不會有結果**。若要更大的樣本，得在本 repo 自己造語料，而不是等別人回報。

### 一個值得照抄的量測紀律（下游 2026-08-17 提供）

回報者當日連續踩到四次「假通過」——檢查本身失效時，輸出與真通過完全相同：regex 沒抓到目標清單卻回報「缺少：無 ✓」、測試容器零輸出卻回報「未洩漏 token ✓」、fixture 沒建成卻讓三個併發 opener 各建新 DB 全部 `rc=0`、監看抓「最新一筆 workflow run」而新 tag 還沒推於是把上一版的成功回報成這一版的。

他們的處置值得照抄：**解析不到就 assert（讓檢查在自己失效時中斷）**、**要求輸出行數大於零**、**把訊號綁在被觀測對象而非「最近一筆」這種會漂移的代理上**。

**本 repo 的自檢結果**：`scripts/release.sh` 的 workflow 監看用的是 `gh run list --branch "$tag"`，綁定在該 tag 而非「最新一筆」，所以第四種陷阱躲過了（已查證，非假設）。而本 issue 的量測**踩過第一種的變體**——第一次重現時暫存語料已被 `/tmp` 清掉，`recall` 走 `!existsSync` 早期返回、回傳空結果，那組全 0 差點被當成有效觀察，是 `latency_ms: 0` 才露出破綻。回報者說「小樣本時這類陷阱的殺傷力比大樣本高」，本 issue 的 12 題正是小樣本。
